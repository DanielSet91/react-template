# Developer onboarding

This is a client-side React + TypeScript template. Run the projects demo without
a backend, then use it as a reference for your own features.

## Start locally

Use Node 22.13 or newer. From the repository root:

```sh
npm ci
npm run setup
npm run dev
```

Open <http://localhost:3000/projects>. Try creating, editing, and deleting a
project. Demo data resets when you reload the browser.

For a new application, use `npm run setup -- my-app` instead of `npm run setup`.
This also renames package and lockfile metadata and updates the HTML title.
Setup preserves an existing `.env`; if yours does not enable mocks, set
`VITE_ENABLE_MOCKS=true` to try the demo without a backend.

On PowerShell, use `npm.cmd` if execution policy blocks `npm`.
See [README.md](README.md) for Docker development and production deployment.

`src/mocks/handlers.ts` to change mock responses.

## Build your first feature

```sh
npm run generate:feature -- orders
```

This creates `src/pages/OrdersPage.tsx`, `src/features/orders/api.ts`, and a
registered `/orders` route. The generator refuses to overwrite existing files.

1. Adapt the generated Zod schema and endpoint to your feature's data.
2. Add a handler in `src/mocks/handlers.ts` while working without a backend.
   Generated endpoints are not mocked automatically.
3. Add a TanStack `Link` in
   `src/components/mainLayout/components/NavigationBar.tsx` if the page belongs
   in the main navigation.
4. Follow the projects example for forms, mutations, detail loaders, and
   invalidating cached lists after changes.
5. Add focused tests for important behavior and run `npm run check`.

## Implementation conventions

- Use TanStack Query for server data and React state for local UI state.
  Redux is not installed. Zod validates data; it does not manage application state.
- Keep feature query keys, query options, and API functions together. Loaders
  and components should share those options and the same Query client.
- Send requests through `apiClient` and pass query abort signals to Ky.
  Ky retries are disabled; configure retries in TanStack Query when needed.
- Validate API responses with Zod. `.json<Type>()` alone does not validate data
  at runtime. For responses without a body, do not call `.json()`.
- Build forms with React Hook Form and the Zod resolver. Reuse `FormTextField`
  for MUI inputs with validation messages.
- Use MUI components and theme values for shared styling. Use MUI `Button`
  directly for ordinary buttons.
- Handle loading, empty, and error states. Reuse `errorMessage` and the toast
  infrastructure for consistent feedback.

## Connect a backend

Update `.env`, replace the example URL with your backend address, and restart Vite:

```dotenv
VITE_API_BASE_URL=http://localhost:8000
VITE_ENABLE_MOCKS=false
```

Requests originate in the browser. Use a browser-accessible URL and configure
the backend to allow the frontend origin for cross-origin requests.

All `VITE_` configuration is public. Keep secrets out of these variables and
local environment files out of version control. Production embeds the API URL
at build time, so URL changes require rebuilding. Mocks run only in development.

The optional helpers in `src/features/auth/session.ts` and
`src/features/uploads/upload.ts` require backend endpoints. They are not a
complete login or upload feature. See the backend contracts in
[README.md](README.md#starter-features).

## Verify your changes

| Command                | Purpose                                           |
| ---------------------- | ------------------------------------------------- |
| `npm run check`        | Lint, production build, and all automated tests.  |
| `npm test`             | Watch the Vitest feature tests.                   |
| `npm run test:run`     | Run feature and setup/generator tests once.       |
| `npm run test:scripts` | Run only setup/generator tests.                   |
| `npm run build`        | Check TypeScript and create the production build. |
| `npm run lint`         | Check ESLint rules.                               |

Add tests for core behavior rather than every file. Existing tests demonstrate
CRUD requests, response validation, form validation, and a complete UI flow.
CI runs build, lint, and tests on pushes and pull requests.

Before opening a pull request, review the diff, preserve unrelated changes,
and document new commands or configuration. Read [AGENTS.md](AGENTS.md) for
repository-specific conventions.
